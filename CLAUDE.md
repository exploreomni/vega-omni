# Working in this repo

This is **`exploreomni/vega-omni`**, a GitHub fork of `vega/vega` with Omni-specific patches. Read [`README-OMNI-FORK.md`](./README-OMNI-FORK.md) for the full picture before making non-trivial changes.

## Branch hygiene

- **Always branch from `omni/main`**, never from `main`. `main` is a pristine mirror of upstream.
- PRs target `omni/main`, not `main`.
- Don't add commits directly to `main` or `omni-dist`. `main` is force-reset to `upstream/main` during sync; `omni-dist` is regenerated by the release script.

## Patch stack discipline

`omni/main` is a **linear stack of patches anchored on the most recent upstream release tag** (e.g. `v6.2.0`). The release script's drift guard refuses to tag if this anchor is wrong.

When upstream cuts a new release, the maintainer rebases the stack onto the new tag:

```bash
git rebase --onto v6.3.0 v6.2.0
```

If you find yourself anchored on `upstream/main` HEAD instead of a release tag, the fix is:

```bash
git rebase --onto v<release> upstream/main HEAD
```

## Local dev

```bash
DISABLE_POSTINSTALL_SCRIPT=1 npm install
```

(`DISABLE_POSTINSTALL_SCRIPT=1` skips a `rsync` of vega-datasets into docs/ that requires extra setup.)

Lerna symlinks subpackages into `node_modules/`, so edits to `packages/vega-*/` are immediately picked up by the umbrella build.

To exercise just one subpackage's tests:

```bash
npx lerna run test --scope vega-scenegraph
```

To rebuild the umbrella package:

```bash
npx lerna run build --scope vega
```

## Releasing

After merging a PR into `omni/main`:

```bash
./scripts/release-omni.sh omni.<N>     # next release suffix
git push origin omni-dist --tags
```

The release script:

1. Validates the patch stack is anchored on a release tag (drift guard)
2. Runs the full monorepo build
3. Verifies the umbrella ESM bundle has no surviving `from 'vega-*'` imports
4. Stages a slim `package.json` (keeps `vega-typings` as a runtime dep — the umbrella's `index.d.ts` requires it)
5. Updates `omni-dist` with built artifacts and tags `v<upstream>-omni.<N>`

## Upstreaming a patch

```bash
git checkout -b upstream-pr/foo upstream/main
git cherry-pick <sha-from-omni-main>
git push origin upstream-pr/foo
# Open PR via GitHub UI: exploreomni/vega-omni:upstream-pr/foo → vega/vega:main
```

The fork relationship to `vega/vega` was preserved by `gh repo fork`, so PRs to upstream don't need a separate user-level fork.

## Common tasks for agents

| Task | Approach |
| --- | --- |
| Add a feature to a subpackage | Edit `packages/vega-<name>/src/...`, test with `npx lerna run test --scope vega-<name>`, commit on a branch off `omni/main`, PR. |
| Fix a bug in OffscreenCanvas / canvas-detection | These commits live on `omni/main`. Fix on a new branch off `omni/main`; if the original commit needs editing, prefer `git rebase -i` to amend in place. |
| Pull a new upstream release | See `README-OMNI-FORK.md` § "How to pull upstream". |
| Cut a new omni release | See above. |
| Investigate a consumer regression | The consumer fetches `omni-dist` via git URL. Check what's in `omni-dist`'s tip; verify the source SHA referenced in the release commit; reproduce locally. |

## Things to avoid

- **Don't rename packages back to `@omni-co/*`.** That was the old fork's strategy and it had problems. The current strategy keeps upstream names and bundles all subpackages into the umbrella.
- **Don't publish anything to npm.** The whole point of this fork is to consume via git URL. The `npm publish` scripts inherited from upstream should not be invoked.
- **Don't bump subpackage versions.** They keep their upstream versions. We never publish them.
- **Don't merge `main` into `omni/main`.** Rebase, don't merge. The patch stack must stay linear.
